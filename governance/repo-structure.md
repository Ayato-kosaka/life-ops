# リポジトリ構造の設計（Repository Structure）

life-ops を「人生のオペレーティングシステム」として長期運用・拡張するための構造定義。
このファイルが構造の SoT であり、ディレクトリを増やす・変えるときは必ずここを先に更新する。

## 設計原則

1. **タスクの SoT は GitHub Issues**。リポジトリはタスクを持たない。
2. **検討・議論はリポジトリに置かない**。検討は Issue・AIセッション・会話の中で行い、揮発させる。リポジトリに載るのは**確定したものだけ**。
3. **「不変の記録」と「更新される現在」を分ける**。
   - 意思決定の記録（decisions/）＝ Append-only。一度確定したファイルは書き換えず、覆すときは新しい決定を積む。
   - 参照情報（knowledge/）＝ Living document。常に「現在有効な事実」だけを保ち、古くなったら書き換える。
4. **レイヤーで切り、話題で散らかさない**。ファイルの置き場所は「それは何か（ルール？決定？事実？道具？）」で決まる。「何についてか（仕事？お金？）」はレイヤー内のサブディレクトリで表現する。
5. **浅く始めて、必要になってから掘る**。空ディレクトリの先行作成はしない。knowledge のドメインは、そこに置く最初のファイルが生まれた時点で作る。

## レイヤー構成

```
life-ops/
├── README.md            # 入口。全体像と各レイヤーへの案内のみ（詳細は各レイヤーへ）
├── governance/          # 憲法層：運用ルール・構造定義・ラベル設計
│   └── repo-structure.md
├── decisions/           # 決定層：確定した意思決定の記録（ADR形式、連番、不変）
│   └── NNNN-<slug>.md
├── knowledge/           # 事実層：確定済みで現在有効な参照情報（更新型）
│   ├── assets/          # 持ち物・機材の仕様、選び方、購入履歴
│   ├── legal/           # 税務ポジション・法人・EXIT設計
│   └── platform/        # 外部サービスの事業体要件・決済レール
├── prompts/             # 実行層：生成AIに渡す運用プロンプト（朝会・夕会・週報 等）
└── templates/           # 型層：Issue・決定記録などのテンプレート
```

### 各レイヤーの責務と判定基準

| レイヤー | 入るもの | 入らないもの | 変更方針 |
|---|---|---|---|
| `governance/` | 運用ルール、ラベル設計、この構造定義 | 個別の決定・事実 | 随時更新（ルール変更はコミットで履歴化） |
| `decisions/` | 「AとBを比較してAに決めた」という**決定そのもの**＋根拠の要約 | 検討過程の資料・調査ダンプ | **Append-only**。覆すときは新番号で `Supersedes: NNNN` |
| `knowledge/` | 決定の**結果として今有効な事実**（例：法人の登記情報、口座一覧、契約先） | 期限切れの事実、検討メモ | 常に最新へ上書き（履歴はgitが持つ） |
| `prompts/` | AI運用プロンプト | — | 随時改善 |
| `templates/` | 各種テンプレート | — | 随時改善 |

### decisions/（意思決定記録）の運用

- ファイル名：`NNNN-<slug>.md`（ゼロ埋め4桁連番＋英語kebab-caseスラグ。例 `0001-legal-entity-and-exit-design.md`）
- テンプレート：`templates/decision-record.md`
- ステータスは `提案中 → 承認 →（必要なら）廃止（Superseded by NNNN）` の一方向。
- **本文は「結論・理由・影響・再検討トリガー」を1〜3画面に圧縮**する。調査の全文は載せない（出典リンクと担当Issue/セッションへの参照で足りる）。
- 承認の権限は本人のみ。AIは起案までを行い、承認は本人がステータスを変えるか承認の意思を明示して行う。

### knowledge/ のドメイン分割（必要になってから作る）

**現在あるドメイン**

| ドメイン | 扱う範囲 |
|---|---|
| `assets/` | 持ち物・機材。自分のサイズ、選ぶ基準、購入履歴と耐久実績 |
| `legal/` | 税務ポジション、法人・契約、ビザ、EXIT設計 |
| `platform/` | 外部プラットフォームの事業体要件・決済レール・API制約 |

**将来の想定ドメイン**：`finance/`（口座・保険・資産）、`work/`（事業・プロダクト）、`health/`。

ドメインを新設するときは、この表に追記してから作る。空ディレクトリを先に作らない。

## 命名・書式規約

- ディレクトリ・ファイル名：英語 kebab-case。日付は `YYYY-MM-DD`。
- 本文：日本語。見出しは `#` 階層を守る。1ファイル1主題。
- リンク：Issue は `#NN`、決定は `decisions/NNNN` で相互参照する。

## このリポジトリに載せないもの

- 検討資料・調査レポートの全文（→ Issue かAIセッションに置き、決定記録から出典リンクで参照）
- 会話ログの全文（→ 確定した要約のみ Issue へ）
- 認証情報・トークン・口座番号などのシークレット（リポジトリの公開設定に関わらず不可）
- 他人の個人情報
